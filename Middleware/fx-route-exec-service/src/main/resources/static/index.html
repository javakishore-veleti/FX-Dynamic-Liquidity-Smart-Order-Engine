FX Dynamic Liquidity & Smart Order Routing

fx-route-exec-service:8083

Send and record the trade. After qualify picks allowed LPs, this service chooses where to send size, writes the parent order and child LP slices, can failover if an LP rejects, and keeps a trace of what happened.

1. Overview

Service port 8083 · dedicated database fx_route_exec_db

Plain rewrite of the hard sentence: “Take a qualified FX order, send pieces of it to one or more liquidity providers (LPs), save the big order and each LP slice, and later show a full history of how it was filled.”

2. Plain-language glossary

Route / route-and-execute

Route = decide where the order (or slices of it) should go among LPs. Execute = actually attempt the fill and record the result. API: POST /api/v1/fx/orders/route-execute.

LP (liquidity provider)

A bank or market-maker that can take the other side of the FX trade. In this repo the ranked demo LPs are LP_CITI, LP_JPM, LP_GS (plus INTERNAL_BOOK when the bank fills from its own book).

Venue

Same idea as in qualify: a trading destination — here, an LP (or internal book). “Child venue split” = one slice of the parent order aimed at one venue/LP.

Parent order

The client’s whole order as one record in fx_execution_orders (total notional, pair, side, overall status, executed rate, slippage, mode). One parent can have many children.

Child / split / child venue split

A split is one piece of the parent size assigned to one LP. Stored in child_venue_splits with allocatedNotional, fill rate, hold latency, LP status.

Parent wants $10M. Child A: $5M to Citi. Child B: $5M to JPM. Those are two child venue splits.

LP allocation

How much notional each LP gets. Modes in this service include:

  • Single LP — all size to the top-ranked LP
  • MULTI_LP_SWEEP — size split across multiple LPs (e.g. half / half)
  • INTERNAL_BOOK — filled inside the bank, not external LP

Allocations differ by strategy, LP rank, available size, and later failover decisions — not every LP always gets the same amount.

TCA (not “TCI”)

Transaction Cost Analysis — after-the-fact review of how good the fill was (rate, slippage in bps, which LPs, latency). In this API the “trace” endpoint is the provenance/TCA view: GET /api/v1/fx/orders/{clientOrderId}/trace.

Provenance / trace

The audit story of the order: parent status, execution mode, child splits, evaluated LPs, rule version. Answers “what happened to client order CO-123?”

When do we say a fail?

A fail (rejection) on a child means that LP did not accept/fill that slice — common demo status: LAST_LOOK_REJECTED (LP looked at the order at the last moment and said no). The parent order may still succeed overall if another LP takes the size via failover. Full parent failure is when no path remains to fill the required notional.

Outage (LP outage)

From this repo’s perspective: the LP is temporarily unusable for fills — down, rejecting, timing out, or last-look refusing. Not necessarily the whole bank offline; it means “this venue cannot take our child order right now.”

Impact: that child’s size is at risk; without failover the client may get a partial fill or delay; with failover, size is moved to the next LP so the parent can still complete, possibly with different rate/latency/slippage.

Resolution when there is an LP outage

In this codebase the operational fix is failover, not waiting forever on the dead LP:

  1. Detect fail on the child (e.g. status LAST_LOOK_REJECTED / timeout / outage signal).
  2. Call POST /api/v1/fx/orders/{orderId}/failover with the rejected LP id.
  3. Service marks that LP’s split as rejected and creates a new child split on the next ranked LP (waterfall: Citi → JPM → GS).
  4. Parent may move to MULTI_LP_SWEEP so remaining size can complete elsewhere.
  5. Trace/TCA later shows both the failed path and the successful failover path.

If every LP in the path is in outage / rejects, there is no further automatic resolution in this service — the parent cannot fully fill until an LP recovers, credit/qualify is re-run, or ops escalates (e.g. halt venue via admin, wait, or cancel).

Resolution picture: primary road closed → divert traffic to the backup road (failover). If all roads are closed → stop / escalate; you cannot invent a new city.

Path / failover path

A path is a planned route of venues (e.g. try Citi first, then JPM, then GS). A failover path is the backup route used when the primary LP fails/outages. API: POST /api/v1/fx/orders/{orderId}/failover — mark the rejected LP, create a new child split on an alternate LP, switch mode toward multi-LP sweep as needed.

Elevator picture: primary elevator (Citi) breaks → take the stairs/next elevator (JPM). Failover path = the backup route you planned for outages.

3. Business features

  • Route-and-execute the parent order after qualify
  • Create child venue splits (LP allocations)
  • Failover to another LP when one rejects / is in outage
  • TCA / provenance trace by client order id

4. Database tables

Database: fx_route_exec_db

  • fx_execution_orders — parent order (transactional execution record)
  • child_venue_splits — per-LP allocation / fill slices
